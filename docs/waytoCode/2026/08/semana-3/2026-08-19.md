### E1 — `textoBadge(tarjeta, alternativo)` — ✅ Completado (1 fallo)

- **❌ Error conceptual:** en la rama donde el badge existe, en vez de LEER su texto lo SOBREESCRIBÍA con un valor fijo (`=` en vez de comparación/lectura) — el test 1 pasaba de casualidad porque el texto real del badge de prueba ya era "Nuevo".

!!! failure "❌ Código de Pau (intento 1)"
    ```js
    function textoBadge(tarjeta, alternativo) {
     let badge = tarjeta.querySelector(".badge")
     return badge ? badge.innerText = "Nuevo" : alternativo; // ❌ asigna, no lee — y hardcodea el texto
    }
    ```

!!! success "✅ Versión corregida"
    ```js
    function textoBadge(tarjeta, alternativo) {
     let badge = tarjeta.querySelector(".badge")
     return badge ? badge.textContent : alternativo;
    }
    ```

🧠 **Lección:** un test que pasa no siempre significa que el código esté bien — si el dato de prueba coincide por casualidad con un valor hardcodeado, el fallo queda tapado. Mismo patrón de fallo silencioso que ya se vio en Symfony (`flush()` sin `$em->`, fecha por defecto de Twig): hay que verificar el dato contra la lógica real, no solo contra "¿dio el resultado esperado esta vez?". Antes de esto, también hubo un desliz momentáneo devolviendo el texto del `alternativo` hardcodeado en vez de la variable recibida por parámetro — autocorregido antes de fijar el código en el archivo.

### E2 — `productosVisibles(lista)` — ✅ Completado (4 fallos)

- **❌ Error 1:** clase mal escrita en el selector — `.productos` (con "s") en vez de `.producto`, la real en el HTML. `querySelectorAll` no avisa si no encuentra nada, devuelve una colección vacía en silencio.
- **❌ Error 2:** comparaba `e.classList` (un objeto `DOMTokenList`) contra el string `"producto oculto"` con `!==` — nunca son iguales, así que el filtro dejaba pasar todo siempre.
- **❌ Error 3:** dentro de una función flecha con llaves `{ }`, faltaba el `return` explícito en varias ramas — sin él, la función devuelve `undefined` (falsy) y `filter()` descarta todo.
- **❌ Error 4:** intentaba llamar `.map()` sobre `e` (un único elemento `<li>`) dentro del propio `filter()` — `map()` es un método de array, no de un elemento suelto; además lo que se hace `return` dentro de `filter()` solo decide si el elemento se queda o no, nunca reemplaza al elemento en el array resultante.

!!! failure "❌ Código de Pau (varios intentos)"
    ```js
    // intento 1 — clase mal escrita + comparación inútil
    function productosVisibles(lista) {
      let filtro = lista.querySelectorAll(".productos"); // ❌ la clase real es "producto"
      let listaNueva = [...filtro];
      return listaNueva.filter(e => e.classList !== "producto oculto"); // ❌ objeto vs string, nunca son iguales
    }
    ```
    ```js
    // intento 2 — condición correcta invertida + sin return + sin extraer texto
    function productosVisibles(lista) {
      let listaNueva = [...lista.querySelectorAll(".producto")];
      let listaFiltro = listaNueva.filter(e => {
       if (e.classList.contains("producto")) // ❌ TODOS tienen esta clase, no filtra nada
        return e.textContent;
       // ❌ sin return si la condición es falsa
      });
      return listaFiltro; // ❌ sigue siendo un array de elementos, no de textos
    }
    ```
    ```js
    // intento 3 — contains() con dos clases juntas + map() mal ubicado
    let listaFiltro = listaNueva.filter(e => {
     if (!e.classList.contains("producto oculto")) // ❌ contains() espera UNA clase, no dos con espacio
      e.map(e => e.textContent) // ❌ e es un elemento, no un array — y sin return, tampoco sirve
    });
    ```

!!! success "✅ Versión corregida"
    ```js
    function productosVisibles(lista) {
      let filtro = lista.querySelectorAll(".producto")
      let listaNueva = [...filtro].filter(e => !e.classList.contains("oculto"))
      return listaNueva.map(e => e.textContent)
    }
    ```

🧠 **Lección:** `filter()` y `map()` son dos pasos separados y con responsabilidades distintas — `filter()` decide QUÉ elementos se quedan (sin transformarlos), `map()` transforma cada elemento en OTRA cosa. Meter la lógica de `map()` dentro del `filter()` es un error conceptual común. Y `classList.contains()` siempre espera el nombre de UNA sola clase — nunca una cadena con varias clases separadas por espacio.

### E3 — `siguienteItem(menu)` — ✅ Completado (1 fallo)

- **❌ Error conceptual:** el orden de las líneas leía `opcion.nextElementSibling` ANTES de comprobar si `opcion` existía — cuando ningún `<li>` tiene la clase `activo`, `opcion` es `null` y esa lectura explota, sin llegar nunca al chequeo de `!opcion` que estaba una línea más abajo.

!!! failure "❌ Código de Pau (intento 1)"
    ```js
    function siguienteItem(menu) {
      let opcion = menu.querySelector(".activo")
      let hermano = opcion.nextElementSibling // ❌ lee de "opcion" antes de comprobar si existe
      if(menu.lastElementChild === opcion || !opcion) return null
      else
        return hermano.textContent
    }
    ```

!!! success "✅ Versión corregida"
    ```js
    function siguienteItem(menu) {
      let opcion = menu.querySelector(".activo")
      if(menu.lastElementChild === opcion || !opcion) return null
      let hermano = opcion.nextElementSibling
      return hermano.textContent
    }
    ```

🧠 **Lección:** cuando algo puede no existir, el chequeo de existencia tiene que ir ANTES de cualquier línea que toque una propiedad de ese algo — no alcanza con que el chequeo esté "en algún lugar" de la función, el ORDEN importa. Mismo patrón que el Fallo de Selección de la teoría (comprobar `null` antes de usar `.addEventListener`), aplicado ahora a navegación por el árbol DOM.
