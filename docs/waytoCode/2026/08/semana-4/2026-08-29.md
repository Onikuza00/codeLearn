### P1 — Setup Tailwind + arreglar la entidad `Product` — ✅ Completado (4 fallos)

- **❌ Confundir la capa de tipo PHP con la de tipo de columna Doctrine:** `private ?decimal $price` / `private ?TEXT $description`. `decimal` y `text` no son tipos de PHP — van dentro del atributo (`type: Types::DECIMAL`), no en el type-hint. El type-hint de un `DECIMAL` es `?string` (Doctrine lo devuelve como string para no perder precisión).
- **❌ `use` equivocado:** faltaba `use Doctrine\DBAL\Types\Types;` y se añadió `use Symfony\Component\Form\Extension\Core\Type\{TextType, DecimalType};` — copiar la forma del `use` agrupado desde el doc de Formularios, con el namespace del contexto equivocado (form types, no DBAL types). `DecimalType` como form type ni existe.
- **❌ `length: 255` dejado en la columna `TEXT`** — `TEXT` no lleva `length`.
- **❌ Falta el `__construct()`** para asignar `createdAt`. Con la columna `DATETIME NOT NULL`, `new Product()` deja `createdAt` en `null` y el `persist()` peta.

!!! failure "❌ Intento"
    ```php
    #[ORM\Column]
    private ?decimal $price = null;          // ❌ decimal no es tipo PHP

    #[ORM\Column(length: 255)]
    private ?TEXT $description = null;        // ❌ TEXT no es tipo PHP; length sobra
    ```

!!! success "✅ Corregido"
    ```php
    use Doctrine\DBAL\Types\Types;

    #[ORM\Column(type: Types::DECIMAL, precision: 10, scale: 2)]
    private ?string $price = null;

    #[ORM\Column(type: Types::TEXT)]
    private ?string $description = null;

    public function __construct()
    {
        $this->createdAt = new \DateTimeImmutable();
    }
    ```

🧠 **Lección:** dos capas distintas. El **type-hint de PHP** solo admite tipos PHP (`string`, `int`, `\DateTimeImmutable`...). El **tipo de columna** va dentro de `#[ORM\Column(type: ...)]` y ahí viven `decimal`/`text`. El puente: `DECIMAL` ↔ `Types::DECIMAL` ↔ `?string`. Y un nombre de clase sin `\` delante se resuelve contra el namespace del archivo, no el global — por eso cada clase usada necesita su `use` con el namespace correcto.

### P4 — Controlador `GET/POST /product/new` (de memoria) — ✅ Completado

- **✅ Flujo de memoria correcto:** `new Product()` → `createForm` → `handleRequest` → `if (isSubmitted && isValid)` → `persist`+`flush`+redirect → `render` en el else. Las 6 piezas, sin apuntes.
- **❌ `ProductType` no importado** → fatal (mismo patrón que P3).
- **❌ `redirectToRoute('/tareas')`** — dos errores: `redirectToRoute()` habla en **nombres de ruta, no URLs** (Symfony genera la URL a partir del nombre); y esa ruta no existía (había borrado `index()` entero). `/tareas` además es de otro bloque.

!!! failure "❌ Intento"
    ```php
    return $this->redirectToRoute('/tareas');   // ❌ path, no nombre de ruta; y no existe

    // index() restaurado:
    public function index()                     // ❌ sin : Response
    {
        return $this->redirectToRoute('product_index');  // ❌ se redirige a sí misma
    }
    ```

!!! success "✅ Corregido"
    ```php
    #[Route('/product/new', name: 'product_new', methods: ['GET', 'POST'])]
    public function new(Request $request, EntityManagerInterface $em): Response
    {
        $product = new Product();
        $form = $this->createForm(ProductType::class, $product);
        $form->handleRequest($request);

        if ($form->isSubmitted() && $form->isValid()) {
            $em->persist($product);
            $em->flush();
            return $this->redirectToRoute('product_index');
        }

        return $this->render('product/new.html.twig', ['form' => $form]);
    }

    public function index(): Response
    {
        return $this->render('product/index.html.twig', []);
    }
    ```

🧠 **Lección:** `redirectToRoute()` recibe el **nombre** de la ruta, no la URL — es como llamar a una función por su nombre, no por su código. Y una acción que redirige a su propia ruta es un bucle infinito. El flujo de memoria salió; los fallos fueron todos de superficie (imports, naming inglés, plantilla).

### P5 — Controlador `GET/POST /product/{id}/edit` (de memoria) — ✅ Completado (3 fallos, 2 rondas)

- **✅ Concepto central de memoria:** `flush()` **sin `persist()`** — la entidad viene ya gestionada por Doctrine (la trae el `EntityValueResolver` por el type-hint), modificarla y sincronizar alcanza.
- **❌ Ruta malformada `'/product/edit{id}'`** — falta la barra: `'/product/{id}/edit'`. Como estaba, matcheaba `/product/edit5` pegado.
- **❌ `methods: 'POST'`** — falta `GET`. El `edit` sirve dos cosas: `GET` muestra el form relleno, `POST` lo guarda. Con solo `POST`, entrar desde el navegador → 405.
- **❌ `Product $Product` vs `$product`** — las variables de PHP distinguen mayúsculas; `$product` estaba indefinida.

🧠 **Lección:** `persist()` = "empezá a seguir este objeto nuevo"; `flush()` = "sincronizá lo que ya seguís". La entidad de `edit` viene de la BD → ya la sigue Doctrine → `flush()` basta (dirty checking → UPDATE). El `edit` es GET+POST por la misma razón que el `new`.

### P6 — `base.html.twig` con Tailwind, mobile-first — ✅ Completado (6 fallos, 6 rondas)

- **❌ `sticky` sin `bg-*` ni `z-10`** → header transparente, el contenido pasa por detrás al scrollear.
- **❌ Tailwind CDN dentro del `{% if frankenphp_hot_reload %}`** → solo carga con esa variable de entorno. Con `symfony serve` normal, Tailwind no existe y **ninguna clase funciona**.
- **❌ Logo como `<div class="logo">` vacío** (clase inexistente, div invisible) — 3 rondas hasta ponerlo como `<a>` con texto. En un intento: anchors anidados `<a><a></a>`.
- **❌ Estructura de bloques invertida:** `{% block body %}` envolviendo el `<main>` (y antes header+footer enteros) en vez de al revés. 3 rondas hasta que cuadró.
- **❌ `max-w5xl`** (falta el guion) → sin ancho máximo, `mx-auto` no centra.
- **❌ Footer `border-t border-2 border-black`** — `border-2` pone borde en los 4 lados y pisa a `border-t`.

!!! failure "❌ Intento (estructura de bloques)"
    ```twig
    {% block body %}
       <header>...</header>
       <main class="mx-auto max-w-5xl px-4 py-8"></main>
       <footer>...</footer>
    {% endblock %}
    ```

!!! success "✅ Corregido"
    ```twig
    <body>
        <header class="sticky top-0 z-10 flex items-center justify-between bg-sky-500/90 p-2">...</header>
        <main class="mx-auto max-w-5xl px-4 py-8">
            {% block body %}{% endblock %}
        </main>
        <footer class="border-t py-2 text-center text-sm text-gray-500">...</footer>
    </body>
    ```

🧠 **Lección:** un `{% block %}` es un **hueco vacío**. Lo que está *alrededor* del hueco es fijo (se queda en todas las plantillas hijas); lo que está *dentro* lo reemplaza cada hija. Si querés que `<main>` con sus clases sea permanente, `<main>` va alrededor y el bloque dentro. Y `sticky` no pinta fondo — sin `bg-*` + `z-*` el header es transparente.

### P7 — `product/index.html.twig`: grid responsive — ✅ Completado (8 fallos, 5 rondas)

- **❌ Controlador:** `TareaRepository $tareaRepository` (no importado, entidad equivocada) en vez de `ProductRepository`. `->FindAll()` con mayúscula.
- **❌ `{% for products in item %}`** — sintaxis al revés. Es `{% for CADA_UNO in LA_LISTA %}`; `item` no existía y machacaba el array `products`.
- **❌ `{% else %}` fuera del `{% for %}`** (después del `{% endfor %}`) → `else` sin `if`/`for`.
- **❌ Clases inventadas:** `color-sky-600` (es `text-*`), `text-semibold` (es `font-semibold`), `text-2x1` (es `text-2xl`), coma dentro del `class=""`.
- **❌ `text-color-sky-600`** — pegar la corrección (`text-`) encima de la rota (`color-`) sin borrar la vieja.
- **❌ `<ul class="flex flex-col">` dentro del `<div class="grid">`** — el grid tiene un solo hijo (el `ul`), que apila todo en vertical → el grid no hace nada.
- **❌ `<div class="grid">` en cada tarjeta** — el `grid` copiado al hijo (marcado 5 veces).
- **❌ `bg-sky-500/40` de debug** dejado en el grid 4 rondas seguidas.

!!! failure "❌ Intento"
    ```twig
    <div class="grid gap-6 sm:grid-cols-2 lg:grid-cols-3 bg-sky-500/40">
    <ul class="flex flex-col gap-2, list-none">
    {% for products in item %}
    <li class="text-base text-semibold color-sky-800">{{ item }}</li>
        {% endfor %}
    {% else %}
    <h2 class="color-red-400">No hay productos.</h2>
    </div>
    ```

!!! success "✅ Corregido"
    ```twig
    <div class="grid gap-6 sm:grid-cols-2 lg:grid-cols-3">
    {% for item in products %}
        <div>{{ item.name }}</div>
    {% else %}
        <h2 class="text-sm font-normal text-red-400">No hay productos a mostrar.</h2>
    {% endfor %}
    </div>
    ```

🧠 **Lección:** `{% for X in LISTA %}` — `X` es cada elemento, `LISTA` la colección; invertirlos rompe todo en silencio. El `{% else %}` va **dentro** del `for`, entre el cuerpo y el `{% endfor %}`. En Tailwind el color de texto es `text-*` y el peso `font-*` — no existe `color-*` ni `text-semibold`. Y un grid maqueta a sus **hijos directos**: meter un `<ul flex-col>` en medio lo anula.

### P8 — `product/_card.html.twig`: componente + `include` — ✅ Completado (4 fallos, 2 rondas)

- **✅ Mecanismo del `include` y `number_format` bien planteados.**
- **❌ `{% include ... with { prod: product } %}`** — `product` no existe; la variable del bucle es `item`. Se le pasaba `undefined` a la tarjeta.
- **❌ `</div>` suelto** residual del `<div>{{ item.name }}</div>` viejo → etiquetas desbalanceadas, cierra el grid antes de tiempo.
- **❌ `prod.precio`** en vez de `prod.price` — la propiedad de la entidad está en inglés.
- **❌ Clases:** `border-5` (no existe: `border`/`-2`/`-4`/`-8`), `text-red` sin tono, `font-base` (no existe: `text-base` o `font-normal`), `class="grid"` en la tarjeta otra vez, falta `p-5`.

🧠 **Lección:** el `with { clave: valor }` del `include` — `valor` tiene que ser una variable que exista en ese punto (dentro del `for`, es `item`, no `product`). Al cambiar el contenido de un elemento hay que revisar sus etiquetas de cierre. Y en Tailwind los anchos de borde son una escala cerrada (`border`, `border-2`, `border-4`, `border-8`) — `border-5` no existe.

### P9 — Badge de stock + estados `hover`/`group` — ✅ Completado (4 fallos, 3 rondas)

- **✅ Preguntó por `group` antes de escribir** — buena señal.
- **❌ `{% if prod.stock === 0 %}`** — `===` no existe en Twig, se compara con `==` (`===` es de JS/PHP).
- **❌ Etiquetas del badge al revés:** `stock == 0` → "En stock" verde, `else` → "Agotado" rojo. Es al contrario.
- **❌ `group` mal montado:** `group-hover:text-blue-600` puesto en la tarjeta (que **es** el group, no un hijo) y faltaba la marca `group` en el `<div>`.
- **❌ Over-correction:** al quitar el `group-hover:` de la tarjeta, borró también `transition hover:shadow-md hover:-translate-y-0.5` (el efecto propio de la caja).
- Menor: `<h2>` sin `transition` → el cambio de color con `group-hover:` es un salto seco.

!!! success "✅ Patrón `group`"
    ```twig
    <div class="group rounded-xl border p-5 transition hover:shadow-md hover:-translate-y-0.5">
        <h2 class="font-semibold transition group-hover:text-blue-600">{{ prod.name }}</h2>
        {% if prod.stock == 0 %}
            <span class="... bg-red-100 text-red-700">Agotado</span>
        {% else %}
            <span class="... bg-green-100 text-green-700">En stock</span>
        {% endif %}
    </div>
    ```

🧠 **Lección:** `hover:` reacciona al hover del **propio** elemento. Para "hover en el padre → cambia un hijo": la palabra `group` (una marca) en el padre, y `group-hover:` en el hijo. El `hover:` sin prefijo sigue yendo en el padre para efectos sobre el padre mismo. Twig compara con `==`, nunca `===`.

### P10 — Borrar con formulario + token CSRF — ✅ Completado (2 fallos)

- **❌ `$request->request->get1('_token')`** — typo `get1` por `get`.
- **❌ `name="token"` en el input vs `->get('_token')` en el controlador** — los dos extremos del cable con nombres distintos → el controlador recibe `null` → `isCsrfTokenValid(intención, null)` → siempre falla → nunca borra. Se resolvió cambiando el controlador a `token` (funciona, pero `_token` es la convención de Symfony).

!!! success "✅ Las dos piezas"
    ```twig
    <form method="post" action="{{ path('product_delete', { id: prod.id }) }}">
        <input type="hidden" name="_token" value="{{ csrf_token('delete' ~ prod.id) }}">
        <button>Borrar</button>
    </form>
    ```
    ```php
    #[Route('/product/{id}/delete', name: 'product_delete', methods: ['POST'])]
    public function delete(Request $request, Product $product, EntityManagerInterface $em): Response
    {
        if ($this->isCsrfTokenValid('delete' . $product->getId(), $request->request->get('_token'))) {
            $em->remove($product);
            $em->flush();
        }
        return $this->redirectToRoute('product_index');
    }
    ```

🧠 **Lección:** el `name` del input oculto y el string que lee el controlador (`->get('...')`) son los dos extremos del mismo cable — tienen que ser idénticos. La **intención** (`'delete' ~ id` en Twig = `'delete' . $id` en PHP) también tiene que coincidir en los dos sitios. Un `<a>` hace GET y no lleva token → cualquier web podría incrustarlo y borrar por vos; el form + token es lo que protege.

### P11 — `ProductType` con opción propia `is_edit` — ✅ Completado (2 fallos)

- **✅ `buildForm` correcto a la primera:** cadena `->add()->add()` → `;` → `if ($options['is_edit'])` → seguir con `$builder->add()`. El `if` es una sentencia, no encaja dentro de la cadena fluida, pero `$builder` es el mismo objeto y podés llamarle `->add()` en sentencias separadas.
- **❌ Faltaba `['is_edit' => true]`** como tercer argumento de `createForm()` en el `edit()`.
- **❌ `stock` de la entidad sigue en `= null`** — al no recogerlo el form de `new`, crear un producto petará con "stock cannot be null". Pendiente ponerlo en `private ?int $stock = 0;`.

🧠 **Lección:** una opción propia en `configureOptions()` (`setDefaults(['is_edit' => false])`) que `buildForm()` lee para decidir qué campos montar — el patrón `esAdmin`/`esEdicion`. Un mismo `Type`, dos comportamientos según quién lo crea.

### P12 — Buscador sin entidad + QueryBuilder — ✅ Completado (3 fallos)

- **✅ Preguntó bien por dónde viene `term`:** del form vía `handleRequest($request)`, no de `$request->query->get()` directo ni de un parámetro de ruta.
- **❌ Repository:** sin return type `: array`; `setParameter('nombre', $term)` **sin los `%`** → `LIKE` sin comodines es prácticamente un `=` (buscar "camis" no encuentra "Camiseta"); placeholder `:nombre` vs argumento `$term` incoherente.
- **❌ Controlador: faltaba la condición** `$term ? findByNameLike($term) : findAll()` (lo identificó él).
- **❌ `render(view, ['products' => ...], ['searchForm' => ...])`** — el tercer argumento de `render()` es un `Response`, no un segundo array de variables. Las dos claves van en el mismo array.

!!! success "✅ Corregido"
    ```php
    // Repository
    public function findByNameLike(string $term): array
    {
        return $this->createQueryBuilder('p')
            ->andWhere('p.name LIKE :term')
            ->setParameter('term', '%' . $term . '%')
            ->getQuery()
            ->getResult();
    }

    // Controlador index()
    $form = $this->createForm(ProductSearchType::class, null, ['method' => 'GET']);
    $form->handleRequest($request);
    $term = $form->get('term')->getData();

    $products = $term
        ? $productRepository->findByNameLike($term)
        : $productRepository->findAll();

    return $this->render('product/index.html.twig', [
        'products' => $products,
        'searchForm' => $form,
    ]);
    ```

🧠 **Lección:** un form sin `data_class` recoge datos sueltos — `$form->get('term')->getData()` te da el string crudo. `LIKE` necesita los `%` explícitos para "contiene". `render()` recibe **un** array de variables para la plantilla; el tercer parámetro es un `Response`, no más variables.

## 🔎 Por qué fallaron — resumen del día

Hilos comunes, ninguno de teoría:

1. **Aplicar media corrección.** Arreglar una parte de lo señalado y dejar el resto en su sitio (P2, P4, P7). Reincidencia directa de "copiar la forma correcta al sitio equivocado" (Fallos 12, 41, 49 de `GOTCHAS.md`), ahora en PHP, Twig y Tailwind.
2. **Decir "así?" / "listo" sin releer ni guardar.** Varias rondas con el archivo idéntico al anterior o con la corrección a medias. En P7 se le pasó el bloque entero para pegar y editó 2 de 5 cosas a mano.
3. **Clases Tailwind inventadas.** `color-*`, `text-semibold`, `font-base`, `border-5`, `text-red` sin tono, `text-2x1`. Reps de sintaxis pendientes — van en la card de maquetación básica de Tailwind, aparte.
4. **Imports que faltan.** `Types`, `ProductType`, `IntegerType` usados sin `use` → clase no encontrada en el namespace del archivo → fatal (P1, P3, P4).
5. **Confundir capas.** Tipo PHP vs tipo de columna Doctrine (P1); nombre de ruta vs URL (P4); variables de plantilla vs `Response` en `render()` (P12).

**Lo que sí salió de memoria y bien:** el flujo completo de los controladores `new` y `edit` (las 6 piezas, `flush` sin `persist`), la estructura cadena/`;`/`if` de `buildForm` en P11, y parar a preguntar por `group` (P9) y por dónde viene `term` (P12) antes de escribir.
