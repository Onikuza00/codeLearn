### E1 — `formularioValido(datos)` — ✅ Completado (1 fallo)

- **❌ Error conceptual:** validaba contando cuántas propiedades tenía el objeto en total (`Object.values(datos).length !== 3`) en vez de comprobar los tres campos concretos por su nombre. Esto acopla la validación a "cuántas claves hay", no a "qué claves hay" — un objeto con 3 claves cualesquiera pasaba, y el mismo objeto con un 4º campo válido (ej. `telefono`) fallaba aunque `nombre`/`email`/`password` estuvieran bien.

!!! failure "❌ Código de Pau (intento 1)"
    ```js
    function formularioValido(datos) {
     let info = Object.values(datos);
     if(info.length !== 3) return false; // ❌ cuenta claves, no valida CUÁLES claves
     return info.every(e => e.length > 0) ?? false; // ?? false nunca se activa: .every() jamás devuelve null/undefined
    }
    ```

!!! success "✅ Versión corregida"
    ```js
    function formularioValido(datos) {
     if(datos.nombre && datos.email && datos.password){
     let info = Object.values(datos);
     return info.every(e => e.length > 0);
     }
     else
      return false;
    }
    ```

🧠 **Lección:** cuando el enunciado pide validar campos concretos de un objeto, hay que acceder a esos campos **por su nombre** (`datos.nombre`, `datos.email`...), no inferir su presencia contando cuántas propiedades tiene el objeto — el conteo es un proxy indirecto que se rompe en cuanto el objeto tiene una forma distinta a la esperada.

### E3 — `posicionEnCarrito(carrito, id)` — ✅ Completado (1 fallo)

- **❌ Error conceptual:** le pasó a `findIndex()` una comparación ya resuelta (`carrito.id == id`) en vez de una función. JS evalúa esa comparación una sola vez, antes de llamar a `findIndex` — como `carrito` es el array completo (no tiene `.id`), da `false`, y `findIndex(false)` revienta porque `false` no es invocable.

!!! failure "❌ Código de Pau (intento 1)"
    ```js
    function posicionEnCarrito(carrito, id) {
      return carrito.findIndex(carrito.id == id) ?? -1; // ❌ pasa un booleano ya evaluado, no una función por elemento
    }
    ```

!!! success "✅ Versión corregida"
    ```js
    function posicionEnCarrito(carrito, id) {
      return carrito.findIndex(e => e.id == id) ?? -1;
    }
    ```

🧠 **Lección:** `find`/`findIndex`/`filter`/`map`... reciben una **función callback** que el método ejecuta una vez por cada elemento del array — no una condición ya evaluada contra el array entero. El parámetro de esa función (`e` en este caso) representa "el elemento actual", nunca el array completo. Nota aparte: el `?? -1` sigue sin activarse nunca (mismo caso que el `?? false` del E1) — `findIndex` siempre devuelve un número, jamás `null`/`undefined`.

### E11 — `ConfiguracionInvalidaError` + `leerConfiguracion(json)` — ✅ Completado (2 fallos)

- **❌ Error conceptual 1:** la relación entre las dos piezas estaba invertida — `leerConfiguracion` construía y devolvía siempre un `ConfiguracionInvalidaError`, sin intentar `JSON.parse` por su cuenta ni distinguir el camino válido del inválido. Además usaba `return` en vez de `throw` para el error.
- **❌ Error conceptual 2:** el constructor de `ConfiguracionInvalidaError` no llamaba a `super(mensaje)` antes de tocar `this` — obligatorio en toda clase `extends`, porque `this` no existe hasta que se inicializa la parte heredada.

!!! failure "❌ Código de Pau (intento 1)"
    ```js
    class ConfiguracionInvalidaError extends Error {
      constructor(mensaje) {
        try {
          JSON.parse(mensaje); // ❌ no es trabajo de la clase parsear nada
        }catch(error){
          return "ConfiguracionInvalidaError" + error; // ❌ constructor derivado no puede devolver un string
        }
      }
    }

    function leerConfiguracion(json) {
      ConfiguracionInvalidaError(mensaje); // ❌ clase llamada sin "new", y "mensaje" no existe
    }
    ```

!!! success "✅ Versión corregida"
    ```js
    class ConfiguracionInvalidaError extends Error {
      constructor(mensaje) {
       super(mensaje)
       this.mensaje = mensaje;
      }
    }

    function leerConfiguracion(json) {
      try {
          return JSON.parse(json);
        }catch(error){
          throw new ConfiguracionInvalidaError(error);
        }
    }
    ```

🧠 **Lección:** en un `try/catch`, el `try` va donde está la operación que puede fallar de verdad (`JSON.parse`) — la clase de error personalizado no ejecuta lógica, solo construye un objeto descriptivo con `super(mensaje)`. Y `throw` corta la ejecución y obliga a quien llama a capturarlo; `return` simplemente entrega un valor como si nada hubiera pasado — no son intercambiables cuando el enunciado pide "lanzar" un error.

### E12 — `class ProductoDigital extends Producto` — ✅ Completado (2 fallos)

- **❌ Error conceptual 1:** `super(nombre)` solo reenviaba uno de los dos parámetros que `Producto` necesita en su constructor — `precio` quedaba `undefined` dentro del padre.
- **❌ Error conceptual 2:** los métodos `descripcion()` usaban `nombre`/`precio` sueltos (los parámetros del constructor) en vez de `this.nombre`/`this.precio`. Un parámetro del constructor solo existe mientras se ejecuta el constructor — otro método de la clase no tiene acceso a él, solo a lo que quedó guardado en `this`.

!!! failure "❌ Código de Pau (intento 1)"
    ```js
    class Producto {
      constructor(nombre, precio) {
        this.nombre = nombre;
        this.precio = precio;
      }
      descripcion() {
        return `${nombre} --${precio}`; // ❌ nombre/precio no existen aquí, solo this.nombre/this.precio
      }
    }

    class ProductoDigital extends Producto {
      constructor(nombre, precio, urlDescarga) {
       super(nombre); // ❌ falta reenviar "precio"
       this.urlDescarga = urlDescarga;
      }
      descripcion() {
        return `${nombre} --${precio}(descarga digital)`; // ❌ mismo problema de scope
      }
    }
    ```

!!! success "✅ Versión corregida"
    ```js
    class Producto {
      constructor(nombre, precio) {
        this.nombre = nombre;
        this.precio = precio;
      }
      descripcion() {
        return `${this.nombre} — ${this.precio}€`;
      }
    }

    class ProductoDigital extends Producto {
      constructor(nombre, precio, urlDescarga) {
       super(nombre, precio);
       this.urlDescarga = urlDescarga;
      }
      descripcion() {
        return `${this.nombre} — ${this.precio}€ (descarga digital)`;
      }
    }
    ```

🧠 **Lección:** `super(...)` tiene que reenviar TODOS los argumentos que el constructor del padre espera, en el mismo orden — si falta alguno, esa propiedad queda `undefined` en el padre. Y los parámetros de un constructor son locales a ese constructor: para que el resto de la clase pueda usarlos, primero hay que guardarlos en `this` (`this.nombre = nombre`), y después acceder siempre vía `this.nombre`, nunca por el nombre suelto del parámetro.

### E4 — Hero centrado — ✅ Completado (1 fallo)

- **❌ Error conceptual:** usó `items-center` para centrar el bloque, pero el enunciado pedía también el texto centrado (`text-align`), una propiedad distinta. Con el texto corto del ejercicio no se nota, pero si el párrafo se partiera en dos líneas quedarían pegadas a la izquierda dentro de su caja.

!!! failure "❌ Código de Pau (intento 1)"
    ```html
    <section class="flex flex-col justify-center items-center gap-2 min-h-screen">
      <!-- ❌ falta text-center: items-center centra la CAJA, no el texto dentro -->
    ```

!!! success "✅ Versión corregida"
    ```html
    <section class="flex flex-col justify-center items-center text-center gap-2 min-h-screen">
    ```

🧠 **Lección:** `items-center`/`justify-center` posicionan la caja del elemento dentro del contenedor flex; `text-align` (Tailwind: `text-center`) alinea el contenido de texto DENTRO de esa caja. Son dos mecanismos distintos que suelen combinarse, no uno sustituye al otro.

### E5 — Footer con bloques de enlaces — ✅ Completado (3 fallos)

- **❌ Error conceptual 1:** `flex-col` (sin prefijo) se aplica en TODOS los breakpoints al no tener un `md:flex-row` que lo sobreescriba — en desktop los tres bloques seguían apilados en vez de ir lado a lado.
- **❌ Error conceptual 2:** `w-100` no existe en la escala de Tailwind (llega hasta `w-96`) — la clase no generaba ningún CSS, el "igual ancho" no se cumplía.
- **❌ Error conceptual 3:** `justify-between`/`items-center` en los `div` internos no hacían nada porque esos `div` no eran contenedores flex — les faltaba `flex flex-col` a ellos mismos.

!!! failure "❌ Código de Pau (intento 1)"
    ```html
    <footer class="flex-col md:flex gap-2 items-center justify-center">
      <!-- ❌ flex-col sin override a md:flex-row → sigue en columna en desktop -->
      <div class="w-100 justify-between items-center">
        <!-- ❌ w-100 no existe · falta flex flex-col en este div -->
    ```

!!! success "✅ Versión corregida"
    ```html
    <footer class="flex flex-col md:flex-row gap-2 items-center justify-center">
      <div class="flex flex-col flex-1 items-center justify-between">
    ```

🧠 **Lección:** en Tailwind, una clase sin prefijo de breakpoint se mantiene activa en TODOS los tamaños salvo que la sobreescribas explícitamente (`md:`, `lg:`...) — mobile-first es "base + overrides", nunca "base solo para móvil". Y `flex-1`/`justify-*`/`items-*` solo tienen efecto sobre HIJOS DIRECTOS de un contenedor que sea `flex` — aplicarlas en un elemento que no es flex container no hace nada.

### E6 — Card de precio con etiqueta — ✅ Completado (1 fallo)

- **❌ Error conceptual:** usó `align-center`, que no existe en Tailwind (confundió el nombre de la propiedad CSS `align-items` con la utility, que es `items-center`).

!!! failure "❌ Código de Pau (intento 1)"
    ```html
    <div class="flex flex-col gap-2 justify-center align-center text-center ...">
      <!-- ❌ align-center no es una clase de Tailwind, no hace nada -->
    ```

!!! success "✅ Versión corregida"
    ```html
    <div class="flex flex-col gap-2 justify-center items-center text-center ...">
    ```

🧠 **Lección:** el prefijo `items-*` es la utility de Tailwind para `align-items`; `align-*` en Tailwind existe pero es para `vertical-align`, una propiedad distinta. Escribir una clase que "suena lógica" pero no está en el vocabulario real de Tailwind no da error visible — simplemente no genera CSS y queda muerta.

## 🔎 Por qué fallaron — resumen del día

7 de 18 ejercicios con fallos reales (E1, E3, E11, E12 en JS; E4, E5, E6 en Tailwind). En JS, la misma raíz de siempre: pasarle a algo **menos información de la que necesita, o del tipo equivocado** (callback vs. booleano evaluado, conteo vs. campos concretos, argumento de menos en `super()`, parámetro de constructor tratado como visible fuera de él). En Tailwind, primera práctica real de maquetación: confundir utilities con nombres de propiedades CSS (`align-center` en vez de `items-center`), no entender que las clases sin prefijo de breakpoint persisten en todos los tamaños (mobile-first como "base + overrides"), y no notar cuándo una utility de flex no tiene efecto porque el elemento no es un contenedor flex.

No son patrones nuevos de `GOTCHAS.md` — son la primera práctica intensiva con clases/herencia (JS) y con maquetación real en Tailwind (CSS), así que estos fallos son esperables en terreno todavía poco pisado.
