## 🧠 Errores más importantes

!!! failure "❌ Decidir la estructura de datos por cuántas propiedades tiene la entidad"
    Patrón recurrente en los tres casos: «la entidad tiene X campos, entonces necesito una entidad de unión / un índice / un DTO». El número de propiedades de la clase no decide nada.

🧠 **Lección:** cada decisión de estructura sale de una fuente distinta y ninguna es la clase. Las columnas de un índice salen del `WHERE` y el `ORDER BY` de las consultas frecuentes. La entidad de unión sale de si la **relación** guarda un dato propio (una fecha de alta, un rol dentro del equipo). El DTO sale de qué **campos pinta** una pantalla. Siempre se mira qué hace el sistema con los datos.

!!! failure "❌ Mezclar capas de contextos distintos"
    Dos mezclas concretas: `SameSite` (atributo de **cookie**) con CORS (cabecera `Access-Control-Allow-Origin` de la **API**); y firewall (**autenticación** — valida firma y caducidad del token) con voter (**autorización** — consulta la BD y decide sobre un objeto).

🧠 **Lección:** son capas que se ejecutan en momentos y sitios distintos. Un token válido siempre pasa el firewall aunque el usuario ya no tenga el permiso; quien lo para es el voter. `SameSite` protege la cookie de sesión; CORS decide qué orígenes de navegador acepta la API (lista explícita, nunca `*`).

!!! failure "❌ Devolver `403` en un recurso con dueño"
    `403` cuando el pedido 48 no es del usuario. Ese `403` **confirma que el pedido existe**, y alguien puede recorrer IDs (`/1`, `/2`, `/3`...) para mapear los pedidos ajenos.

🧠 **Lección:** en recursos con dueño se devuelve `404` — no distingue «no existe» de «no es tuyo». El `403` se reserva para «no tienes el rol para esta sección entera», donde no se oculta la existencia de nada.

!!! failure "❌ Tratar el adaptador y el servicio como dos piezas anidadas"
    Buscar «un conector dentro del servicio» para hablar con el ERP. Y dar por resuelto que el ERP se caiga solo con poner un timeout.

🧠 **Lección:** el adaptador **es** el servicio — una sola clase que contiene el formato del ERP, los timeouts, los reintentos, la caché y el cortocircuito; la lógica de negocio vive fuera. El timeout limita **una** llamada (3-5 s); el cortocircuito deja de llamar **del todo** tras varios fallos seguidos, para que no haya cien procesos bloqueados a la vez. Se usan juntos.

!!! failure "❌ Querer resolver el timeout de PHP con promesas"
    Plantear `async`/promesas para no bloquear la petición mientras se espera al ERP.

🧠 **Lección:** las promesas son de JavaScript. En PHP/Symfony el modelo es síncrono: el timeout es una **opción de configuración** de la llamada HTTP (`['timeout' => 5]`). Lo que descarga la petición del trabajo pesado es una **cola** + worker en segundo plano, no la asincronía del lenguaje.
