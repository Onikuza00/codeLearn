## My Workflow — Photo to Landing, Step by Step

-1. **First thing after cloning the voraData repo, before anything else:** check `opencode.json`'s `dgx-spark` provider entry for a `maxTokens`/`max_tokens`/`options.maxOutputTokens` field. Verified empirically on 2026-09-16 (direct test against `http://voradata-ia.hopto.org:30000`) that the served model (`qwen38-27b`, confirmed via `/v1/models` despite `.env` saying `qwen38-flash-next` — reconcile that naming too, see below) is a reasoning/thinking model: it burns a large chunk of the token budget on an internal `reasoning_content` field before writing the actual answer. At `max_tokens: 300` it used 273 on reasoning and got cut off mid-sentence (`finish_reason: "length"`). If this project's default is unset or low (SDK defaults are often 256-512), every real generation call (HTML sections, especially in Phase A/C below) risks being truncated mid-output. Set it generously (at minimum ~1500-2000+ for a single component; more for a full-page skeleton) and re-verify with a real prompt that `finish_reason` comes back `"stop"`, not `"length"`, before trusting the workflow below.
   - **Latency finding, same test:** a single image+code generation at `max_tokens: 1500` took **192 seconds** (still cut off, 1086 tokens spent on reasoning alone) — roughly 7-8 tokens/sec. Likely cause: the DGX Spark's unified LPDDR5x memory (~273 GB/s bandwidth) is far below a data-center GPU's HBM (several TB/s), and autoregressive decoding is memory-bandwidth-bound, not compute-bound — so despite the Spark's high advertised TOPS, per-request generation speed is slow regardless of prompt tuning. Budget ~2-4 real minutes of wait per generation call across the 48h sprint (Phase A/B/C/D each make several calls) — don't plan the schedule assuming cloud-API-like response times. Mitigations to test: (a) keep per-phase prompts asking for code output only, not prose description + code, (b) check whether the endpoint honors a "disable thinking" toggle (Qwen3-style `enable_thinking: false` param or a `/no_think` prompt instruction) for simpler sections where the reasoning overhead isn't worth the wait.
   - **Mitigation verified and confirmed working:** passing `"chat_template_kwargs": {"enable_thinking": false}` in the request body dropped the same task from 192s to **14.2s** — a ~13x speedup, `finish_reason: "stop"` (complete, not truncated), `reasoning_tokens: 0`. This should be the default for Phase A-C generation calls, where speed matters and tasks are fairly mechanical once the design-system tokens are in the prompt. Reserve thinking mode (`enable_thinking: true` / omitted) for a specific section that keeps coming out wrong and needs more deliberation.
   - **Two caveats from the same fast-mode test, not free wins:** (1) without thinking, it still defaulted to Tailwind's stock palette (`bg-blue-600`/`bg-yellow-400`) instead of any brand token — confirms fix #8 applies regardless of thinking mode, the design-system must always be in the prompt. (2) it produced `style="min-height: 250px;"` inline — a direct violation of the no-inline-CSS rule in `normas/` that the slower reasoning-mode test didn't make. Faster generation trades away some rule adherence; the per-phase human review gate stays mandatory in fast mode, not optional.
   - **Where to configure it in OpenCode — not yet confirmed, action item for whoever clones the repo first:** `enable_thinking` isn't a UI toggle, it's a field (`chat_template_kwargs: {enable_thinking: false}`) in the JSON body sent to `/v1/chat/completions`. For OpenCode to send it automatically, it needs to live in the `dgx-spark` model/provider entry in `opencode.json` — providers built on `@ai-sdk/openai-compatible` typically expose a pass-through field for extra body params (commonly `options`, `body`, or `extraBody` depending on SDK version) that gets merged into every request to that model. Could not verify the exact key — the voraData `opencode.json` isn't cloned on this machine yet (checked 2026-09-16, nothing local). First thing to do once it exists: open that file, find the `dgx-spark` model block, and check whether the schema supports a pass-through body option. If OpenCode's schema doesn't expose one at all, fall back to asking whoever manages the SGLang deployment to set `enable_thinking: false` as the server-side chat-template default, so it applies without per-call config — infra territory, not yours to change directly.
   - **Same test also confirmed the risk in #8 below is real, not hypothetical:** the model correctly read the test image's color (`#2563EB`, exact match) but wrote it as `bg-[#2563EB]` — an arbitrary value pulled straight from the pixel — instead of a design-system token, because none was given in that isolated test. Confirms: every real prompt must include the current `design-system/` tokens or this happens by default.

5. Iterate in structure-first order (greyboxing — cheap to fix structure, expensive to fix detail), human-on-the-loop review gate at the end of each phase before moving to the next:
   - **Phase A — full-page skeleton, one pass.** Feed all Canvas screenshots together, ask for structure only (which standard component each section maps to, order, heading hierarchy) — no real content, no fine styling. Deliverable: one HTML file, semantic `<header>`/`<main>`/`<section id="...">` per photo/`<footer>`, each section commented with its matching standard component, correct heading hierarchy with placeholder text, no brand color/typography classes, no images, no JS. Width and height are never a per-section decision: width is always the shared container (`max-w-6xl mx-auto px-4 sm:px-6 lg:px-8`; a section needing edge-to-edge background gets a `w-full` wrapper around that same container, content width never changes). Height is always intrinsic — content + the shared `py-20 lg:py-32` token, never a fixed pixel height — except the Hero, which may use `min-h-[80vh]`/`min-h-screen` (min, not fixed, so mobile copy can still grow it) for above-the-fold impact; this Hero variant isn't documented yet in `componentes/`, add it. The Canvas photo is a reference for relative visual weight (this section reads as dominant → more padding within the scale), never a literal pixel spec — placeholder copy in the mockup won't match the client's real copy length. Review gate: is the section order right, is each photo mapped to the correct component, is the heading hierarchy correct? Fix here, not later — this is the cheapest point to catch a wrong call.
   - **Phase B — Header/Navbar + Footer, their own iteration, before any content section.** They're the shared chrome and fix the visual baseline (primary button, brand typography, base spacing) that every later section should inherit instead of reinventing. Deliverable: real Navbar (logo, nav links pointing to the exact `id`s created in Phase A — this is where a mismatched id from A gets caught, CTA using `btn-primary` with the client's real brand color) and real Footer (logo/tagline, legal links, same tokens as the navbar), scroll/sticky behavior as its own JS module under `assets/js/modules/` (never inline, per the norms). This is the concrete point where blocking fix #2 (`btn-primary`/`btn-secondary`/`btn-white` undefined) gets resolved — defined here with real brand data, not in the abstract. Review gate: nav links jump to the correct section ids, CTA contrast passes WCAG AA, mobile menu is keyboard-accessible (`aria-expanded`, visible focus). A bad call here repeats across every Phase C section instead of once.
   - **Phase C — remaining sections, one iteration per section, in page order** (Hero → Features → Social proof/Pricing/FAQ if present → final CTA). Structure and system are already locked from A/B; each iteration here only decides content and section-specific styling. Per-section prompt: image + updated `design-system/` + `componentes/`, explicitly asking the agent to reuse existing tokens instead of inventing values from the image. Review gate per section: tokens reused (no stray hex/classes), `alt` on images, contrast, heading hierarchy from Phase A still intact. If a section needs something not in `componentes/` (a card pattern, a new block type), stop and decide whether it belongs in the preset — don't improvise it ad-hoc and move on.
   - **Phase D — GSAP animation pass, after every Phase C section is closed and the layout is stable.** Not mixed into Phase C: ScrollTrigger positions are computed against the final DOM, so animating before layout/content settle means recalculating triggers on every later content tweak. Init Lenis once, globally, before creating any ScrollTrigger instance — every section's scroll-based animation reads the same scroll source, never a per-section proxy. One iteration per animated section, approved by eye in the browser (timing/easing can't be judged by reading a diff) before moving to the next. This is the concrete point where blocking-adjacent fixes #6 (JS budget vs. GSAP) and #7 (`prefers-reduced-motion`) actually get enforced — check real JS weight once GSAP + plugins are loaded, and gate every timeline behind `prefers-reduced-motion` before considering it done.
   - **Phase E — one final pass over the whole page**, not per section: performance (`loading="lazy"`, JS/CSS weight including GSAP), SEO (meta tags, single `h1`), and a token-consistency check across all sections (this is where drift from a skipped review in Phase C shows up).
6. If a section needs behavior (accordion, dropdown, carousel), have the agent check Preline via MCP for the accessible pattern instead of improvising JS.
7. Manually review each generated section before moving to the next: spacing/hierarchy by eye (the local model isn't pixel-perfect on the first pass), no stray hex/classes outside the tokens, `alt` on images, contrast.

## Future Proposal — Multi-Model Routing per Phase (research-backed, not for tomorrow's build)

Not verified on voraData's own hardware — based on public DGX Spark benchmarks (2026-09-16 research), to bring to whoever owns the DGX infra as a proposal, not something to adopt without testing. Context: on a memory-bandwidth-bound box like the Spark (~273 GB/s unified LPDDR5x, confirmed as the likely cause of the 192s/14.2s latency finding above), **active parameter count decides decode speed, not total parameter count** — a sparse MoE (Mixture of Experts) model with few active parameters per token will consistently outrun a dense model of similar or even smaller total size on this specific hardware.

- **Phase A (skeleton/recognition) + Phase C (per-section content, vision+code):** primary — **Nemotron 3 Nano Omni** (30B total, 3B active, MoE, NVFP4 ~21GB). NVIDIA's own reference model for DGX Spark; natively multimodal (text/image/audio/video), so it covers reading the Canvas photo without a separate vision call. Public benchmarks show ~74-108 tok/s on Spark-class hardware vs. the ~7-8 tok/s measured today on the currently-loaded dense `qwen38-27b`. Alternative: **Gemma 4 26B-A4B-it** (Google, 26B total/4B active, also MoE, vision-capable) — worth benchmarking side by side since it's a different training lineage and might read UI layouts differently.
- **Phase B (navbar/footer) + Phase D (GSAP animation) — pure code, no vision needed:** primary — **Qwen3-Coder-Next** (80B total, 3B active, MoE, 256K context, ~70% SWE-Bench). Purpose-built coding-agent model, same "cheap decode" profile as Nano Omni. Fits the mechanical, instruction-following nature of these two phases (assemble from documented tokens/components, write GSAP following known API patterns) better than a vision-tuned model would. Alternative: none well-verified yet in research — worth checking Nemotron 3 Nano's text-only (non-Omni) variant, same 3B-active profile, in case it handles Tailwind/GSAP idioms better in practice.
- **Phase E (final audit pass) — one pass per page, correctness over speed:** primary — **Nemotron 3 Super** (120B total, 12B active, MoE, 512 experts/22 active per token). More active parameters than the others (~19.5 tok/s on Spark, still MoE-cheap relative to a dense model that size) — justified here specifically because this phase runs once per page, not iteratively, so the extra latency is affordable in exchange for more careful rule-checking (performance/SEO/token-consistency). Alternative: `unsloth/Qwen3.5-122B-A10B` (also MoE, similar class), listed in the same "best for DGX Spark" community collection — untested comparison, but a reasonable fallback if Nemotron 3 Super underperforms in practice.
- **Practical note:** Nano Omni (~21GB) and Coder-Next are both compact enough to plausibly stay loaded together in the Spark's 128GB unified memory without swapping between Phases A-D; Nemotron 3 Super (120B total) likely needs to load on its own for Phase E, accepting one model-swap per page at the very end rather than per section.

**How to route a different model per phase — not SDD, not manual copy-paste between chats:** SDD's phases (`propose → spec → design → tasks → apply → verify → archive`) are for planning *code changes* to the repo — a different concept from these A-E *content-generation* phases, don't conflate the two or force this into SDD ceremony (too much overhead for something repeated every 48h per client). The right mechanism is OpenCode's existing per-agent model assignment — already used elsewhere in this setup: the global `opencode.json`'s `jd-judge-a` and `jd-judge-b` agents each pin a different model (`opencode/mimo-v2.5-free` vs `opencode/hy3-preview-free`) in their own config block. Once the voraData repo exists, define one OpenCode agent per role (e.g. `landing-vision`, `landing-coder`, `landing-auditor`), each with its `model` field pointing at the matching DGX model, and delegate each workflow phase to its agent — the orchestrator routes automatically, no manual model-switching per call.

## Blocking — resolve before writing any page

### 1. Single-page vs multi-page architecture conflict
`presets/landing/componentes/` uses anchor links (`href="#contacto"`, `href="#features"`) — a one-page landing. `presets/landing/normas/` describes a folder-per-section URL structure (`serveis/index.html`, `sobre-nosaltres/index.html`) — a multi-page site. These are two different architectures; a build can't follow both at once.

**Fix:** Decide the default for the landing preset (recommended: single page with anchored sections — that's what "landing" usually means and what fits a 48h delivery). Keep the folder-per-section structure documented only in the SaaS preset, not here.

### 2. `btn-primary` / `btn-secondary` / `btn-white` are used but never defined
Referenced in Navbar, Hero, and CTA component examples. `design-system/` has no `@layer components` (or composed-utility) definition for them.

**Fix:** Add the actual class definitions (either Tailwind `@apply` in `app.css` under `@layer components`, or spell out the full utility string once so it can be copy-pasted consistently) to `design-system/`.

### 3. Neutral color scale has gaps
`design-system/` only defines `--color-neutral-900/800/100/50`. But `componentes/` and `normas/` already use `text-neutral-600`, `text-neutral-500`, `border-neutral-200` — none of which exist in the declared token set, so they silently fall back to Tailwind's default gray instead of the brand's.

**Fix:** Define the full neutral scale (100 through 900, step 100) as `--color-neutral-*` tokens.

### 4. No typography tokens (`--font-*`)
The designer hands over fonts per project via PDF, but `design-system/` has no `--font-heading` / `--font-body` variables — only Tailwind's default `font-*` utility usage. Every new project means hunting every `font-*` class in the HTML instead of swapping two variables.

**Fix:** Add `--font-heading` / `--font-body` (or equivalent) to the `@theme` block, defaulting to a system stack, so a new project only requires updating the token.

### 8. Photo-to-markup workflow has no anchoring rule
Actual delivery flow: designer sends a Canvas screenshot per section, Pau feeds it to the OpenCode agent (DGX Spark, vision-capable `qwen38-27b`) to generate the markup. With an incomplete design-system (see #3, #4), the agent has nothing to map the image against and will pull colors/sizes straight from image pixels — every landing ends up with its own one-off hex values instead of reusing the shared tokens, defeating the point of the design system. This raises #3 and #4 from "important" to "blocking" specifically for this workflow.

**Fix:** Once #3/#4 are fixed, add an explicit instruction to `sdd/landing/` (or a new short doc): the agent must be prompted with the photo **plus** `design-system/` and `componentes/` together, told to identify which standard component each section maps to, and required to reuse existing tokens/classes rather than inventing new values from the image. Cross-check the resulting markup against Preline's catalog for structure/accessibility before treating the vision-model output as final — don't trust local-model image-to-code as pixel-accurate on the first pass; budget a manual spacing/hierarchy pass afterward.

## Important — will be missing at delivery time

### 5. Checklist lists 9 sections, only 5 have example code
`presets/landing/componentes/` checklist includes Social proof, Pricing, and FAQ, but no HTML example exists for any of the three (only Navbar, Hero, Features, CTA, Footer are coded).

**Fix:** Add baseline HTML for Social proof (logo strip), Pricing (table/cards), and FAQ (accessible accordion — `<details>`/`<summary>` or `aria-expanded` pattern) so they don't have to be improvised under a 48h deadline.

### 6. GSAP vs. the 50KB JS budget
`normas/` sets Total JS < 50KB. `ia/gsap/` documents GSAP as an available tool. GSAP core plus any plugin already exceeds that budget alone.

**Fix:** Either state explicitly that the 50KB budget excludes GSAP (and document a separate GSAP-project budget), or restrict GSAP to projects that justify it and use CSS/Web Animations API for standard landings.

### 7. No `prefers-reduced-motion` guidance
Accessibility rules cover WCAG AA contrast, keyboard nav, and aria — but not respecting the OS-level reduced-motion preference, which WCAG 2.1 also requires for animation-heavy pages (relevant given GSAP is in the toolkit).

**Fix:** Add a short rule + snippet to `normas/` (e.g. gate GSAP timelines behind `window.matchMedia('(prefers-reduced-motion: reduce)')`).

## Minor

- **Tailwind config mismatch:** `presets/landing/` file structure lists `tailwind.config.js`, but `design-system/` uses `@theme` in CSS — the Tailwind v4 config-less approach. Pick one and document it explicitly (recommended: pure v4 `@theme`, no JS config, less friction for a fast build).
- **No structured data in SEO rules:** `normas/` doesn't require JSON-LD (`Organization`/`LocalBusiness` schema), even though the documented "Web Quality" skill mentions schema markup. Worth adding for client landings with a local/service business.
- **Intake missing conversion goal + tracking:** `sdd/landing/intake/` doesn't ask for the primary conversion action (book a demo, buy, leave email) or analytics/tracking requirements (GA4, Meta Pixel). Without it, "the main CTA" isn't actually defined.
